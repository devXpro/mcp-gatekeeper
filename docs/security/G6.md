# G6 — the MCP access check (`mcpguard`): security notes

The rules are Family Hub's §5.6 and §5.11, with the T2.R fixes of T2.F3. The package moves them without changing them.

## The access check (`Guard.Middleware`)

- **Bearer token only.** The scheme matches in any letter case. A missing, empty or space-holding credential gets a
  401 without `error=`, and it is not counted as a failure.
- **Valid tokens.** A token passes only when all of these hold:
  - `core.TokenValidator` accepts it for the resource of the path;
  - the token's own `ResourceID` equals that resource (defence in depth against a lenient validator);
  - the person behind the token exists, is active (not disabled and not past their term, `Person.Active`) and is still in the token's account;
  - `ResourceCatalog.Available` says the account may use the resource now (403 otherwise).
- **Dead tokens.** A token the validator refuses (`ErrInvalidToken`, `ErrNotFound`, `ErrExpired` or `ErrUsed`) gets
  401 `invalid_token`. Any other error is the application's own failure: 500, logged without the token.
- **What the 401 says.** It carries
  `WWW-Authenticate: Bearer [error="invalid_token", ]resource_metadata="<PublicURL>/.well-known/oauth-protected-resource<path of the resource>", scope="mcp"`
  (RFC 6750 §3, RFC 9728). The resource id comes from the request path, so it is put in path-escaped. A crafted path
  cannot end the quoted value or add parameters (`TestGuardEscapesTheResourceInTheHeader`). Family Hub's ids are
  plain, so they come out unchanged.
- **Unknown resources.** The middleware does not check that a resource exists. With `PerResource`, an unknown id
  reaches the token check, and every token is refused for it. An application with several resources answers its own
  404 in front of the middleware, as Family Hub does: its registry, then the plain-path rule and the `/hub/` tree.
- **No token in logs, answers or errors.** The only log line is the 500's: `mcpguard: <what>`, with the resource and
  the service's error. The tests check that no token reaches the log.

## The limits

- **Failed credentials.** There is a token bucket of 30 failures (`Options.FailuresPerAddress`) a minute per client address; IPv6 counts per /64,
  and junk that is not an address is cut to 64 bytes. There are at most 4096 buckets: full ones are pruned first,
  then half of the rest.
  - It only turns a refusal into a 429 with `Retry-After`, never a valid token, because the assistants share egress
    addresses (T2.R H2).
  - Every door of the application that takes credentials must call `Guard.Refuse`, so that all failures count
    together.
  - The address comes from `core.ClientIP` under `Site.ClientIP`. The application must make sure that only a trusted
    peer can set the header that mode reads.
- **Calls in flight.** At most 16 calls (`Options.InFlightPerResource`) of one account can be inside one resource at once, open event streams
  included. Every door into the same resource must use `Guard.Admit`. `release` is idempotent, so a place cannot be
  given back twice.
- **Body size.** `ReadBody` takes at most 1 MiB, whether or not `Content-Length` is sent: 413 above that. Since v0.2
  the client also has 30 seconds to send it (408); see [v0.2.md](v0.2.md).

The options and rules added in v0.2 (`MiddlewareFor`, `PerPerson`, ended people not charged to the address) are in
[v0.2.md](v0.2.md).

## Headers

- **The allowlist.** Only these request headers pass: `Content-Type`, `Accept`, `Mcp-Session-Id`,
  `Mcp-Protocol-Version`, `Last-Event-ID`, `Mcp-Method`, `Mcp-Name` and `Mcp-Param-<name>`; a name must be longer
  than the prefix. Everything else stays behind: `Authorization`, `Cookie`, `Proxy-Authorization`, the hop-by-hop
  headers, `Forwarded`, `X-Forwarded-*`, `CF-Connecting-IP`, `Origin`, `User-Agent` and any forged identity or
  request-id header.
- **What comes back.** Only `Content-Type` and `Mcp-Session-Id`. A server's `Set-Cookie`, `Location`,
  `WWW-Authenticate`, CORS headers, CSP, HSTS and `Cache-Control` never come back.
- **What every answer carries.** `X-Content-Type-Options: nosniff`, `Content-Security-Policy: default-src 'none';
  frame-ancestors 'none'; sandbox` and `Cache-Control: no-store`. An event stream gets `no-cache, no-store` instead,
  so that no cache in front of the application (Cloudflare) keeps one family's answer (T2.R M5).
- **Session ids are not bound here.** The application binds `Mcp-Session-Id` to the grant (Family Hub's
  `sessionBinder`, which stays there). An application that serves several people from one MCP server needs that
  binding too.

## Streaming

- **Flushing and pings.** Events are flushed chunk by chunk. A `: ping` comment goes out only between events, after
  25 s of silence (Cloudflare cuts at 100 s).
- **Errors.** A writer that cannot flush is an error rather than a stream that is silently held back.
- **Cancellation.** The stream ends when the assistant's request context ends. The caller makes the upstream request
  with that context, so a client that goes away cancels it.
