# G2 security notes: store/sqlitestore

- **SQL injection:** every value is a bound parameter. The only built SQL is concatenation of constants (column lists, the
  fixed grant-delete statements, the audit page condition); no caller input reaches SQL text. The busy timeout in the DSN is
  a number from `time.Duration`.
- **Secrets at rest:** the adapter stores only what the callers give it, which by contract are sha256 hashes (session ids,
  invite tokens, codes, tokens, client secrets). Nothing is logged except migration steps (component, version, name). Error
  text carries the operation and SQLite's constraint message (table and column names), never a value.
- **File:** the database file is created 0600 and its directory 0700 (SQLite gives `-wal` and `-shm` the main file's mode).
  An existing file keeps its mode; the operator owns it.
- **Atomic one-time use:** invite consume, refresh rotation (reuse is `ErrUsed`, so the caller can revoke the family) and
  code consume are single conditional statements inside a write transaction serialized in the process, with SQLite's own
  write lock across processes; two concurrent calls cannot both win (32-way race tests in `storetest`).
- **Isolation:** a transaction is bound to its `*Store` in the context; a context from another store is not joined.
- **Denial of service:** waiting for the write lock honours the caller's context; a transaction that never returns holds
  the lock (the caller's bug, documented in the package comment); the pool is bounded (default 8 connections).
- **Audit ids** are not secrets and not unguessable; they are cursors only. A malformed cursor is an error, not a restart.
- **Schema from the future** is refused instead of being written to with an older layout.
- Open issue: an application that writes through `Conn` without a transaction bypasses the in-process lock and depends on
  the busy timeout (documented; use `Tx`).
