## OAuth (`oauth`)

One OAuth 2.1 authorization server, its issuer at the application's root (`Site.PublicURL`), for every MCP resource.
It came from Family Hub's `internal/oauth`, with the fixes of Family Hub's security review T2.R (H1, H2, M1, M4, L7,
L8, I4) and the ChatGPT CIMD fix of commit `a0acd6e`. This note replaces Family Hub's `docs/security/T2.1.md` and
`T2.F1.md` for the package; everything they said holds unless it is changed here.

### Resources

- A resource is what one MCP endpoint serves. `Options.Catalog` (`core.ResourceCatalog`) says which resources can be
  connected now (`Resource`, else `core.ErrNotFound`) and whether an account may use one (`Available`).
  `Options.Paths` (`core.ResourcePaths`) gives each its MCP path. Family Hub: `core.PerResource{Prefix: "/mcp/"}`, a
  catalog over its running modules; Homie later: `core.SingleResource{At: "/mcp", ID: "home"}`.
- A resource's RFC 8707 resource is `Site.PublicURL + Paths.Path(id)`, exactly: no trailing slash, nothing below it,
  no query. Its protected-resource metadata is at `/.well-known/oauth-protected-resource` + `Paths.Path(id)` (RFC 9728
  §3.1); every other path under that well-known, the root included, is 404 `{"error":"not_found","message":"no such
  module"}`.
- A resource id that a URL or a scope names must match `^[a-z][a-z0-9-]{1,30}$` before the catalog is asked (Family
  Hub's module id rule). `New` refuses a `core.SingleResource` whose `ID` does not match, so it cannot fail silently.
- A token is bound to one resource: `ValidateAccess(ctx, token, r)` refuses it for any other.

### Secrets and what they unlock

| Secret | Where it lives | What it unlocks |
|---|---|---|
| A client secret (DCR clients that ask for `client_secret_post` or `client_secret_basic`) | the assistant; only its sha256 in the store | the token and revoke endpoints as that client; public clients have none |
| An authorization code | the redirect from approve to the assistant's callback; only its sha256 | one token exchange within 5 minutes, with the PKCE verifier and the same `redirect_uri` |
| An access token | the assistant; only its sha256 | MCP calls to the one resource of its grant, for 1 hour (never past the grant's end) |
| A refresh token | the assistant; only its sha256 | one rotation to a new access and refresh token, within 30 days |
| A transaction id `txn_…` (80 random bits) | the browser's `/consent?txn=…` URL; the process's memory | showing and answering one consent, by a signed-in person in the browser that started it, within 10 minutes, once |
| The binding cookie value (`Brand.TxnCookie`) | the browser (HttpOnly); only its sha256 in the transaction | nothing on its own; the consent API compares it |

Secrets, codes, tokens and binding values are 32 random bytes in base64url. Secrets, the binding and the PKCE
challenge are compared in constant time.

### Clients

- **Callbacks.** An https URL in canonical form (what `url.URL` prints back), without port, user, query or fragment,
  on an exact host: `chatgpt.com` or `chat.openai.com` with `/connector_platform_oauth_redirect` or
  `/connector/oauth/<id>` (`<id>` one segment of `A-Z a-z 0-9 _ -`, at most 128), `claude.ai` or `claude.com` with
  `/api/mcp/auth_callback`. The host tells the assistant. A client has 1 to 10 callbacks, all of one assistant.
  `Options.RefuseConnectorCallback` refuses `/connector/oauth/<id>` everywhere (DCR, CIMD documents, and authorize,
  which checks a stored client again): the mix-up vector of T2.R H1.
- **DCR** (`POST /oauth/register`, RFC 7591): open, as the assistants need it. Bounded by the callback rule (a code
  only ever goes to ChatGPT or Claude), the rate limits, and the deletion of DCR clients without a grant after 1 hour
  (on the next registration). A secret is made only for `client_secret_post` or `client_secret_basic`; other methods
  than those and `none` are refused. The self-chosen `client_name` loses control, format and separator characters and
  is cut to 64 characters. `oauth.client.register` is audited once per client address group a minute; every
  registration is logged.
- **CIMD.** A `client_id` that is an https URL in canonical form, with a path and no dot segments, on `chatgpt.com`,
  `claude.ai` or `claude.com`. Fetched by authorize only, with one GET: 5 s, at most 64 KiB, no redirects, only a 200.
  The document's `client_id` must equal the URL, its callbacks must pass the rules above and belong to the same
  assistant, it must carry no `client_secret`, and its `token_endpoint_auth_method` must be absent or `none` **or**
  list `none` among `token_endpoint_auth_methods_supported` (ChatGPT's real document names `private_key_jwt` and
  supports `none`, `a0acd6e`): the server does not offer `private_key_jwt`, so such a client connects as a public
  client, bound by PKCE and its registered callbacks. Stored and reused 24 hours; when the refetch fails, the stale
  copy is not used. A document that failed or was refused is not fetched again for 5 minutes; one address group
  fetches at most 5 a minute. The fixed host list keeps the fetch from reaching anything else (no SSRF).

### Authorize

- Order: the rate limit; one `client_id` and one `redirect_uri`; the client; the redirect URI exactly one of the
  client's and still allowed by the callback rules. Up to there an error is a page, never a redirect (RFC 6749
  §4.1.2.1). After that, errors go back to the redirect URI with `error`, `error_description`, `state` (when valid)
  and `iss` (RFC 9207).
- `response_type=code`; PKCE S256 with a 43-character challenge (no `plain`, no default); `state` at most 1024 bytes;
  no parameter repeated; `scope` at most 1024 bytes.
- The resource: `resource` names it exactly (`invalid_target` otherwise); one resource only. Without one, a single
  scope `mcp:<id>` may name it (`invalid_scope` otherwise); with one, a scope naming another resource is refused.
  Unknown scopes are ignored; the grant's scope is `mcp`, plus `offline_access` when asked.
- The error pages are bilingual, echo nothing from the request, and carry a CSP of `default-src 'none'` with the
  page's one style allowed by its sha256, `frame-ancestors 'none'`, `base-uri 'none'`, `form-action 'none'`, plus
  `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, `X-Content-Type-Options: nosniff`, HSTS and `no-store`.
  Their title is `Brand.Product`, escaped by `html/template`.

### Pending transactions

- In memory, 10 minutes, answered once. At most 1000 in all, 20 per client address group, 100 per DCR client (none
  per CIMD client: ChatGPT's id is shared by all its users). A new transaction always gets in: over its group's or
  client's bound, that group's or client's oldest goes; in a full store, the oldest of the group holding the most.
  Expired ones go first.
- **Bound to the browser** (T2.R H1), unless `Options.TxnBindingOff`: authorize sets `Brand.TxnCookie` (Family Hub:
  `__Host-fh_txn`) to a random value, `Path=/; Max-Age=600; HttpOnly; Secure; SameSite=Lax`, keeping a well-formed
  value the browser already holds (one value per browser, so two connectors can wait side by side). The transaction
  keeps its sha256. **Lax** is a deliberate exception to the Strict rule of docs/PLAN.md §4.4: the navigation from the
  assistant to authorize is cross-site, and a Strict cookie is not sent on it. The cookie authenticates nothing; it
  is only compared by the consent API, whose calls also need the Strict session cookie and the CSRF checks.
- The transaction notes `started_from` for the consent screen: `assistant` when the `Referer` is an https URL on a
  host of the client's assistant, `elsewhere` for any other `Referer` or `Sec-Fetch-Site: none` (opened directly),
  `unknown` otherwise. A signal, not a check.

### Consent API

- `GET /api/oauth/txn/{txn}`, `POST …/approve` and `POST …/deny` sit behind `Options.Sessions.RequireViewer`
  (package auth): for the writes the CSRF checks first (403 `forbidden`), then 401 `no_session`. The package does
  not repeat them.
- Then, in this order: the transaction (404 `not_found`), the binding (403 `other_browser`, logged as a warning with
  the person, client and resource: phishing looks like this), the resource (404 when it cannot be connected) and its
  availability to the viewer's account (403 `forbidden`). Deny checks only the transaction and the binding. A refusal
  consumes nothing.
- **Approve** reuses the person's active grant of (client, resource) while it is younger than 180 days, or creates
  one (audited), and stores a code valid 5 minutes, all in one store transaction; an outlived grant is revoked
  (audited, `reason: expired`) and replaced. Two approvals racing for a new grant meet at the store's unique index
  and the loser joins the winner's grant. Approve and deny take the transaction out of memory first, so of two calls
  one wins.
- **A new grant needs a fresh step-up** (T2.R M4) unless `Options.ConsentStepUpOff`: `now < Session.StepUpUntil` (a
  sign-in counts for its first 5 minutes); otherwise 403 `step_up_required`, nothing written, and the transaction is
  put back for the retry after the SPA's step-up. Reusing a grant is one click. The decision is taken inside the
  store transaction that finds or creates the grant.

### Tokens

- **Client authentication** (RFC 6749 §2.3): HTTP Basic (form-encoded id and secret) or `client_id` and
  `client_secret` in the form; a public client sends `client_id` alone; one method per request (`invalid_request`).
  A failure is 401 `invalid_client`, with `WWW-Authenticate: Basic realm="<product as a token>"` after a Basic attempt
  (Family Hub: `realm="family-hub"`, derived from `Brand.Product`).
- Requests are form-urlencoded, at most 16 KiB; parameters in the URL query are ignored; none may repeat.
- **The code exchange** runs in one store transaction: consume the code, check it is the client's, the same
  `redirect_uri`, the PKCE verifier (43 to 128 unreserved characters), the `resource` when sent, and a live grant
  younger than 180 days; then store the tokens. A failed check rolls back, so the code survives a wrong try and stays
  with its own client; a store failure leaves it for a retry. A code that comes back after its exchange revokes the
  tokens that exchange issued (RFC 6749 §4.1.2), from an in-memory memo kept for the code's lifetime.
- **Refresh** runs in one store transaction too and rotates: a new access and refresh token in the same family; the
  old access token lives out its hour. A spent refresh token that comes back is reuse: its whole family is revoked
  and `oauth.refresh.reuse` audited, outside the rolled-back transaction and detached from the request, so a client
  that hangs up cannot stop it. A dead token is `invalid_grant` and nothing else. After 180 days the first refresh
  also revokes the grant (audited, `reason: expired`, detached; a failure only logs and the next try revokes it).
- The token and revoke endpoints bound their store work to 7 s and the writes they decide on to 2 s more.
- **Revoke** (RFC 7009): an access token alone, a refresh token with its family; unknown tokens and other clients'
  tokens get the same empty 200.
- **`ValidateAccess`**: a 43-character token only, looked up by its sha256; it must be an access token, not revoked,
  not expired, of a grant that is not revoked, not outlived and for the requested resource, whose client exists.
  Anything else is `core.ErrInvalidToken`; a store failure is returned as itself (the MCP access check answers 500,
  not a sign-in loop). It records the grant's last use at most once a minute. `AccessInfo.ExpiresAt` is never past
  the grant's end.
- `RevokeGrant(ctx, id, actor, ip)` (for the connections API) revokes a grant with all its tokens and audits
  `oauth.grant.revoke`; a revoked grant is left alone; an unknown one is `core.ErrNotFound`.

### Rate limits

Token buckets in memory per client address group (an IPv4 address, or the /64 of an IPv6 one; an IPv4-mapped address
is its IPv4 address; anything that is not an address shares one bucket), the address from `core.ClientIP` under
`Site.ClientIP`:

| Endpoint | Per address group | All addresses |
|---|---|---|
| `POST /oauth/register` | 20 a minute | 60 a minute |
| `POST /oauth/token` | 20 a minute | none (T2.R H2: a shared bucket let three addresses stop every refresh) |
| `POST /oauth/revoke` | 20 a minute | none |
| `GET /oauth/authorize` | 20 a minute | none |
| client ID metadata fetches | 5 a minute | none |

A refusal is 429 with `Retry-After` (`temporarily_unavailable`; a page on authorize).

### Audit

| Action | Account | Actor | Target | Detail |
|---|---|---|---|---|
| `oauth.client.register` | none | none | the client id or CIMD URL | `kind`, `assistant`, `auth_method` (DCR) |
| `oauth.grant.create` | the viewer's | the viewer | the grant | `module`, `assistant`, `client` |
| `oauth.grant.revoke` | the grant's | who revoked (none when expired) | the grant | `module`, `reason` (`expired`) |
| `oauth.refresh.reuse` | the grant's | none | the grant | `module`, `assistant` |

The detail key of the resource stays Family Hub's `module` (docs/PLAN.md §4.2.6). Entries carry the client address,
cut to 64 bytes. No entry and no log line holds a secret, code, token, verifier, binding value or state;
`TestFullFlow` checks every log record and audit entry of a whole flow. Client ids and CIMD URLs are public and are
logged.

### Compatibility with Family Hub (docs/PLAN.md §4.2)

- Everything toward the assistants is byte-for-byte Family Hub's: paths, methods, status codes, headers (including
  `Cache-Control: no-store` with `Pragma: no-cache` and the cookie attributes), the JSON bodies (written with
  `json.Marshal`, as Gin did: HTML characters escaped, no trailing newline) and their texts, which still say "module"
  and "hub". The tests pin the exact bytes of the metadata, an error page, a registration, a token answer and the
  error forms; the golden files are Family Hub's own.
- The one JSON change toward the SPA: the consent view's `module` is now `resource`, with the same inner object.
- Issued codes, grants and tokens keep working: the store records are the same (`AuthCode.Resource` is the same
  resource URL string, the grant's resource id is the module id), and the validation rules did not change.
- The switches are `Options` booleans now; Family Hub maps its `FH_CONSENT_STEPUP`, `FH_OAUTH_TXN_BINDING` and
  `FH_OAUTH_CONNECTOR_CALLBACK` to them (refusing unknown values, as before).

### Known limits

- Transactions, the spent-code memo, the fetch-failure memo and the registration throttle live in memory: a restart
  drops pending consents (people connect again) and forgets spent codes (a code replayed after a restart is refused
  but no longer revokes its tokens).
- The authorize-link variant of consent phishing (the victim's own browser starts the transaction) is left to the
  screen's `started_from` warning and the step-up of a new grant; a phished person who is not signed in signs in with
  a passkey, which counts as the step-up, so the warning is the defence there.
- `started_from` is uncalibrated: an assistant's app that opens the system browser may arrive with
  `Sec-Fetch-Site: none` and no `Referer`, which reads as `elsewhere`.
- A refresh token used twice at once by its own client is reuse (no grace period); watch `oauth.refresh.reuse`.
- A transient failure of an assistant's shared CIMD document blocks that client for 5 minutes.
- About a thousand address groups (a botnet) can still push a real pending transaction out within seconds; that is
  the edge's (Cloudflare's) to stop.
- The CIMD document paths are not pinned per host yet (only the hosts are).
