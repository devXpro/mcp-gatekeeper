# v0.2 — security notes

What v0.2 changed, by package. The notes of v0.1 ([G1](G1.md) to [G7](G7.md)) still hold; the OAuth changes are in
[G4](G4.md) ("A person who may not act", "The person", "The term caps tokens"). Review items are named GK-n.

## Guest terms and permissions: where they are enforced

`core.Person.Active(now)` is `DisabledAt == nil && (AccessUntil == nil || now.Before(*AccessUntil))`. Every place below
uses it, so an ended term and a disabled person look alike from outside.

| Place | Behaviour |
|---|---|
| `auth` session (`Viewer`) | refused (401 `no_session`) and the session row deleted. Step-up, passkey routes and logout sit behind it. |
| `auth` sign-in | after the passkey verified, 403 `access_ended` ("your access has ended; ask the owner to extend it"). No session is created, and it is not counted as a failed sign-in. Only the passkey holder learns the reason. A disabled person still fails like a bad passkey (400 `invalid`). |
| `auth` invites | an invite whose term ended before use is a dead link (404 `not_found`) at the token lookup, `register/begin` and `register/finish` (finish rolls back; the invite stays unused). |
| `oauth` consent, code exchange, refresh | see [G4](G4.md). |
| `mcpguard` (every MCP call) | 401 `invalid_token`, the bytes of a disabled person, and the address bucket is not charged. |

- **The invite is copied inside the redeeming transaction.** `registerFinish` copies `AccessUntil` and `Permissions`
  from the invite that `Consume` returned in that transaction, never from the one read at the start of the ceremony, so
  a change between begin and finish cannot be smuggled in. Two concurrent redeems are serialised by `Consume`: the
  second gets `ErrUsed` (404) and exactly one person exists.
- **Permissions are enforced by the application.** The gatekeeper stores ids and checks them against the
  application's `core.PermissionCatalog`; it never interprets them. `PATCH {access_until: now}` revokes no grants itself
  and relies on the three layers above.
- **GK-13.** A person-level access window is now closed on every path: session, sign-in, consent, exchange, refresh and
  each MCP call. Access tokens never outlive `AccessUntil`.

## `people`: the HTTP side of terms and co-owners

- **A term is never dropped silently.** `New` refuses `Options.Permissions` with an inviter that is not an
  `AccessInviter`. Without a catalog, `access_until` and `permissions` are refused (400), never ignored, and so is
  `role` without `CoOwners`.
- **Widening needs a step-up.** Widening means a later end, no end after having one, or a permission the person lacked
  (`all` covers everything). It is decided inside the store transaction against the person as stored, so a concurrent
  "end now" cannot be undone by a stale narrowing request without a step-up. A refused attempt writes nothing and is not
  audited. Narrowing (an earlier end, fewer permissions, ending now) needs none.
- **Terms are bounded.** An invite's term must be in the future and any term at most one year away. A `PATCH` with a past
  `access_until` is clamped to now. Times are truncated to the millisecond, as the stores keep them, so a stored value
  never later reads as "widening" against itself. Permissions are sorted and de-duplicated, `all` with anything else
  becomes `["all"]`, and an empty list is stored as nil.
- **Superadmin protection.** A `PATCH` on any superadmin is 409, a `PATCH` on yourself is 400, `permissions` on an owner
  is 400, and `DELETE` of a superadmin is 409. The last superadmin cannot be locked out through `PATCH`.
- **Co-owners (`CoOwners`).** Only the superadmin can invite an owner (into its own account only), change or remove an
  owner or a superadmin, withdraw an owner invite, revoke another owner's grant, or delete an account that holds another
  owner. Everyone else gets 403 `forbidden`. Owner invites never carry a term or permissions, and `auth` refuses them
  too. A co-owner is never a superadmin and cannot rename the account through `account_name`.
- **Least exposure.** With a catalog, someone who is not an owner sees `access_until`, `permissions` and `active` on their
  own member row only. The other routes were checked: connections carry neither, the audit shows a member only their own
  entries, and invites, the catalog and `PATCH` are owner-only.
- **Audit.** `account.member.update` records ids only: the role, `access_until` (RFC 3339 or `none`) and the permission
  ids. With co-owners, `account.invite.create` and `account.member.remove` record the target's role. Catalog titles and
  invite tokens never reach the audit.
- **Single account.** `POST` and `DELETE /api/admin/accounts` answer 404 even without a session.

## `mcpguard`

- **GK-1.** `MiddlewareFor(id)` binds the token check to the resource the application routes to and refuses any path
  that maps elsewhere with 404. Plain `Middleware` trusts the application to route on the same uncleaned `r.URL.Path`; the
  probe test shows what a path-cleaning router does to it. `MiddlewareFor` panics at wiring time when the paths cannot
  serve the id.
- **GK-4.** `InFlightPerResource`, `InFlightKey` and `FailuresPerAddress` are options with the old defaults. Under
  `PerPerson`, the bucket that `Admit(w, account, id)` uses is separate from the person buckets, so an application with
  `PerPerson` must admit every door through `AdmitAccess`, or a second door gets its own allowance.
- **GK-12.** A valid token of a person who is gone, disabled or past their term is refused with the same 401 bytes, but it
  is not charged to the per-address failure bucket and is never a 429: the address is an assistant provider's shared
  egress, and a guest whose term was cut must not lock the owner's connector out. The guard skips the bucket only for
  errors that wrap `core.ErrExpired`; it trusts the validator, so a validator that wrapped it for unknown tokens would
  disable the junk-token limit. Still charged: unknown or garbage tokens, a token of another resource, a token whose
  person moved to another account.
- **GK-17.** `ReadBody` and `httpsec.BodyLimit` give a client 30 seconds to send a body (408, `Connection: close`). After
  a timeout the deadline is deliberately left on the connection, so the server's discard of the rest fails fast. On a
  full read it is lifted: otherwise a GET event stream would have its context cancelled 30 seconds in.
- **GK-18.** The texts take `Brand.ResourceWord()`; the defaults keep the old bytes.
- **Logs.** The only new log line is a one-time warning when, in a header client-address mode, a refused request came
  without that header; it carries the header's name only.
- **Known gap.** A term narrowed after a token was issued ("end access now") reaches the guard as a live token of a
  person who is not active; the guard refuses it, charged to the address, until the token's own end (at most an hour).

## `httpsec`

- **GK-2.** `LoopbackPeers()` (`127.0.0.0/8`, `::1/128`) is for a connector on the same machine. It is safe only on a
  listener bound to loopback: any local process can then set `CF-Connecting-IP`, and is trusted as much as the user it
  runs as. Pair `ClientIPCloudflare` with a `PeerGuard` that trusts only the connector. `core.Site.Validate` refuses an
  empty or unknown client-address mode, so a header mode can no longer be forgotten. Quick tunnels are not documented to
  set `CF-Connecting-IP`; if they do not, the TCP peer is the address and every client shares one bucket.
- **GK-19.** `MountClean` is opt-in. It refuses escaped `/` (`%2F`, any case), dot segments and empty segments. A
  `ServeMux` at the top of the application does not need it.
- **GK-14.** Choose a stable RP ID before the first passkey, and prefer the exact host over a parent domain: a parent
  RP ID lets any origin under it ask for the passkeys.

## `auth` and `adminsock`

- **GK-5.** The socket's only proof is the peer's uid, as before. The pid and executable path of the peer (macOS
  `LOCAL_PEERPID` and `kern.procargs2`, Linux `SO_PEERCRED` and `/proc/<pid>/exe`) are recorded in the audit details
  and the log line of `admin.setup-link` and `admin.reset-access`, and never used for access: a pid can be reused and a
  same-uid process can be anything. `auth.Options.OnAccessReset` lets the application alert its owner after a
  successful reset. A same-uid process can already replace the application's binary or read its database, so
  hardening the socket alone buys little. On a desktop, run the application as its own user where you need a real
  boundary. The executable path is a local path of the operator's machine; it lands in the owner-visible audit and in
  the logs, which is the point.
- **Who started the peer (review R-5).** The operator runs `<app> admin …`, so the peer is nearly always the
  application's own CLI, and its path alone says nothing about who asked. Accept also records up to three ancestors of
  the peer, nearest first, as `"<exe> (pid N)"` joined by `" < "` (macOS: `kern.proc.pid` for the parent and
  `kern.procargs2` for the path; Linux: `/proc/<pid>/stat` and `/proc/<pid>/exe`). An ancestor of another user (root's
  `login`) shows only its short command name, and one that cannot be read ends the chain. It goes into
  `adminsock.Peer.Chain`, the detail `peer_chain` of `admin.setup-link` and `admin.reset-access`, and the
  `adminsock: command` log line, only when non-empty: a CLI started straight by `docker exec` has its parent outside
  the container's pid namespace (ppid 0) and records none. Like the pid, it is a trace, never a check: a same-uid
  program can start the CLI from any parent it likes.
- **Setup links in process.** `IssueSetupLink` follows the socket's rule (`core.ErrConflict` while an enabled
  superadmin has a usable passkey of this site; older links revoked) and logs only the expiry. `IssueSetupLinkTTL`
  shortens the life and writes the real end in the store, the return value and the audit.
- **Co-owners.** `auth` never decides who may issue an owner invite (`people` does). Redeeming one for an account that
  already has an owner creates a second owner, not a superadmin, and ignores `account_name`.
- **GK-3.** The hourly sweep calls `store.Purger` when the store has it; errors are only logged.
- **GK-2.** `auth.New` calls `Site.Validate` first.

## Stores

- **GK-3.** `sqlitestore.Purge(now)` runs in one transaction: expired tokens and codes, invites 7 days past their expiry,
  audit entries older than 400 days, and DCR clients without a grant older than an hour. This is what the MongoDB TTL
  indexes do; `mongostore` is unchanged.
- **GK-8.** `Open` sets the database file and its `-wal` and `-shm` to `0600` and the directory to `0700`, and logs a
  warning with the old mode when it had to change one: the data was readable by others until then.
- **Only its own directory (review R-8).** `Open` tightens a directory only when it created it, or when the directory
  belongs to the process user and holds nothing but the database file and its `-wal`, `-shm` and `-journal`. Any other
  directory that is not `0700` (`/tmp`, a home directory, a volume root, an application's data dir with other files)
  is refused with an error that names it, its mode and the reason, and says to use a directory of its own; nothing is
  created or chmodded there. A `0700` directory is used as it is, whatever else it holds.
- **GK-9.** The audit counter is seeded from `MAX(id)` at `Open`, so ids continue after a reopen.
- **GK-11.** `synchronous=FULL`: a committed grant revocation survives a power cut.
- **No new secret at rest.** The new columns and fields hold a date and permission ids.
- **Permissions** are nil when none: `nil` and an empty list read back the same on both adapters.

## `tunnel/cloudflare`: the supervisor

- **The child's environment** is exactly `HOME=<Dir>/home` (a private directory, mode `0700`, deleted and recreated at
  every start, so a `~/.cloudflared/config.yml` of the user can never change or block it) and `PATH=<directory of the
  binary>`. Nothing of the application's environment reaches it (asserted with a canary variable).
- **No secret in argv.** Named mode runs `--config <Dir>/config.yml`, whose credentials file is `0600`; quick mode has
  `--metrics 127.0.0.1:<port> --url <service>` only.
- **The quick host comes from the child's own output only (review R-6).** The metrics port is picked by listen, close,
  reuse, so another local program could bind it in that instant and answer `/quicktunnel` with a host of its own (its
  own quick tunnel in front of the application's port would then see every request in clear). The child's stdout and
  stderr are a private pipe, so the host is read from there; `/quicktunnel` is read afterwards only to confirm it. A
  match is logged at info, a different host at warn (both hosts and the port), no answer at info; none of them changes
  the status or calls `OnURL`. The price is that quick mode depends on cloudflared printing the URL, which every
  release does.
- **The metrics address** must be a loopback IP; the `/quicktunnel` client ignores proxies and reads at most 4 KiB. The
  quick host is accepted only as `<label>.trycloudflare.com`, never `api.`. The named URL comes from `tunnel.json`.
- **config.yml (review R-14).** The credentials path is written as a YAML single-quoted scalar (`'` doubled), so a
  directory name with `: ` or ` #` cannot break or change it. The host and tunnel id are checked before they are
  written and stay plain.
- **The child's output** goes only to the application's log writer. The login link that `Connector.Start` surfaces is
  one-time and for the operator only; the caller must treat it so.
- **Stopping** sends SIGTERM and SIGKILL after 5 seconds.
- **Quick tunnels** carry no uptime promise, no Server-Sent Events and at most 200 requests in flight; `trycloudflare.com`
  is on the Public Suffix List, so the RP ID is the full random host and every new host needs new passkeys.
- `Connector.Start` writes the same files with the same modes as `Connect` and deletes the account certificate on every
  way out.

## UI package

- An ended term is recognised by the code `access_ended`, not by message text; a plain 403 `forbidden` (a CSRF
  refusal) and the 400 of a disabled person keep the generic failure text.
- Without a catalog every screen sends what it sent before, so an application that does not use terms sees no change.
