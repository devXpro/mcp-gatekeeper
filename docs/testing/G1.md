# G1 — store conformance suite and MongoDB adapter: tests

Packages: `store/storetest` (the suite, no tests of its own), `store/mongostore`.

## Unit tests (no Docker)

```sh
make -C <repo> lint test PKGS="./store/storetest/... ./store/mongostore/..."
```

`store/mongostore/store_test.go`: the migrations keep Family Hub's versions and names, the gatekeeper's collection
list, `Options` validation, the URI never in an error (`redactURI`, `New`), the audit cursor check, lossless document
conversions, and that a grant's resource is stored as `module_id` with `revoked_at: null` while active.

## Integration tests (Docker, tag `integration`)

```sh
make -C <repo> integration PKGS="./store/storetest/... ./store/mongostore/..."
make -C <repo> lint PKGS="--build-tags integration ./store/storetest/... ./store/mongostore/..."
```

`TestMain` (`helper_integration_test.go`) starts one throwaway `mongo:8.0 --replSet rs0` container named
`gk-g1-mongo-<random>` on a random port bound to 127.0.0.1, initiates the single-node replica set, runs the tests and
removes the container (`docker rm -f`) whatever happens. Each test gets its own database and drops it. No credentials:
the container has no auth. A leftover after a hard kill: `docker rm -f $(docker ps -aq --filter name=gk-g1-mongo)`.
The whole package runs in about 6 s (the first run pulls `mongo:8.0`).

| Test | What it proves |
|---|---|
| `TestConformance` | `storetest.Run`: the 20 groups below, in parallel, each on its own database |
| `TestCompatIndexes` | a fresh database gets exactly Family Hub's gatekeeper collections and index specs (names, keys, `unique`, `partialFilterExpression`, `expireAfterSeconds`), and `schema_migrations` records 1 and 2 under Family Hub's names |
| `TestCompatRead` | Family Hub's documents, inserted as they are, read back as the expected values |
| `TestCompatWrite` | documents the adapter writes equal Family Hub's field for field and in field order (the audit's ObjectID aside) |
| `TestMigrationsAndIndexes`, `TestAuditTTLIndex` | Family Hub's migration tests, ported: a re-open applies and logs nothing, TTLs, the audit TTL survives a re-open |
| `TestMigrationsAreLogged` | each applied migration is logged through `slog` (`internal/testlog`), never the URI |
| `TestAuditIDsAreObjectIDs` | audit ids stay hex ObjectIDs (Family Hub's audit cursors) |
| `TestSharedDatabase` | `Options.DB` (Family Hub's shared client): `EnsureCollection` is idempotent, an application collection written with the Tx context rolls back with the store, a `Cascade` on an application collection runs inside the delete's transaction (`InTx`), `Close` leaves the shared client connected |
| `TestOpenFails` | an unreachable server fails `Open` without the password in the error |

### The conformance suite (`storetest.Run`)

Accounts, People, Passkeys, Sessions, Invites, OAuthClients, OAuthCodes, OAuthGrantsAndTokens, RevokeGrantsByResource,
UseRefresh and Audit port Family Hub's store tests and add the edges Family Hub's code has but did not test: expiry
at exactly `ExpiresAt`, idle at exactly `now - idle`, the order of revoked/used/expired in `Peek`, the first
revocation time winning for tokens and grants, list orders, a time in another zone coming back in UTC, a disabled
superadmin still counted. The concurrent groups (InviteConsumeConcurrent, ConsumeCodeConcurrent,
UseRefreshConcurrent) run 32 calls at once and require exactly one winner. AuditLimits checks the default 50 and the
cap of 1000. Tx covers commit, rollback, nesting, a nested error, and a store method's own transaction joining the
caller's. TxIsolation requires a reader outside an open transaction neither to see its write nor to wait for it.
TxConflicts runs 12 transactions on one document at once. DeleteCascades builds two accounts with everything
attached and checks what an account delete and a person delete remove, keep (audit) and tell the `Cascade`
(`DeletePerson` for every person, then `DeleteAccount`). CascadeHooks writes through the store from inside a
`Cascade` and fails it at each step: the cascade's write and the whole delete roll back together.

A mutation check done once by hand: running `DeletePerson` with `context.Background()` instead of the delete's context
makes CascadeHooks fail.

## The fixtures (`store/mongostore/testdata/familyhub`)

Written by Family Hub's own `internal/store` code at commit `b0fc38b`, not by hand: one file per collection
(canonical extended JSON, sorted by `_id`) and `indexes.<collection>.json` per collection, Family Hub's own
`modules`, `account_modules` and `legacy_keys` included for G9's reference. The base time is 2036-01-02, so Mongo's
TTL monitor never deletes a fixture during a test. To regenerate (Family Hub stays untouched; the copy is throwaway):

```sh
rsync -a --exclude node_modules --exclude .git --exclude web <family-hub>/ /tmp/g1-fh/
cp <repo>/store/mongostore/testdata/familyhub/generate/dump_integration_test.go /tmp/g1-fh/internal/store/
G1_FIXTURES_OUT=<repo>/store/mongostore/testdata/familyhub \
  go -C /tmp/g1-fh test -tags integration -count=1 -run TestDumpFixtures ./internal/store/
```

The values in `dump_integration_test.go` and in `compat_integration_test.go` (`fixtures()`) must stay equal.
